# ECK 自我進化與可攜技能圖

## 目前真實狀態

ECK 已具備可驗證的「技能層自我改進」，但尚未具備遞迴 AGI 或安全的核心程式自我替換。

| 能力 | 現況 | 啟用條件 |
|---|---|---|
| 自行產生隔離技能程式與測試 | 已實作 | 模型輸出通過靜態安全掃描 |
| Docker 隔離測試 | 已實作 | Docker Worker 可用 |
| 失敗技能自動修復與重測 | 已實作 | 最多 2 次，不能增加權限或刪除測試偽造成功 |
| 技能熱啟用與舊版保留 | 已實作 | 完整隔離測試通過 |
| 可攜技能、經驗、研究與來源 | 已實作 | SQLite、技能原始碼與雜湊清單匯出 |
| 自動修改結構性核心 | 未實作 | 必須先建立候選實驗室與完整回歸閘門 |
| 核心零停機版本交接 | 未實作 | 需要雙核心控制平面與藍綠切換 |
| 自動訓練基礎模型權重 | 未實作 | 需要資料治理、固定評測、回退與硬體升級 |

`/v1/evolution/status` 是機器可讀的真實狀態。介面或模型不得把「路線圖」描述成已驗證能力。

## 已採用：Voyager 式技能優先迴圈

1. 自主課程或人工任務發現能力缺口。
2. 先查詢可攜技能知識圖，避免重造相同能力。
3. 產生最小權限的技能程式與測試。
4. 在唯讀、限記憶體、限 CPU、無主機權限的 Docker Worker 驗證。
5. 失敗時保留反例與測試報告，建立新修正版，不覆寫舊版。
6. 只有通過版本可自動熱啟用；執行仍需現行成功契約與外部證據。

此路徑對應 Voyager 的自動課程、可執行技能庫、環境錯誤回饋與自我驗證，但 ECK 使用本機模型且不依賴付費 API。

## 下一階段提案 A：核心修補候選實驗室

這是下一個最適合 ECK 的方案，採用 Darwin Gödel Machine 的「候選版本樹＋實證選擇」與 SWE-agent 的程式庫操作介面。

1. 從重複失敗、例外、測試失敗與效能退化建立可重現 bug 契約。
2. 在獨立 Git worktree 或複製目錄產生候選修補，不修改線上核心。
3. 沙箱預設無網路、無祕密、無 Docker socket，僅開放候選工作目錄。
4. 執行 lint、型別、單元、整合、驗收、安全、效能與固定能力基準。
5. 以歷史任務做影子重播，檢查正確率、成本、延遲與安全回歸。
6. 保留多個候選與完整差異，不只保留單一路徑，避免局部最佳化。
7. 結構性候選即使全數通過，仍由人類核准後才能進入藍綠切換。

## 下一階段提案 B：雙核心零停機交接

單一 Python 行程無法在不重啟自身的情況下安全替換核心程式。真正零停機需要：

1. 穩定且最小化的不可變控制平面。
2. 版本化 Kernel A／B，其中一個在線、另一個載入同一份唯讀快照做健康檢查。
3. 事件序號與資料庫寫入租約，避免兩個核心同時寫入。
4. 新核心追上事件游標後切換流量；失敗立即回退舊核心。
5. 圖像、影片、瀏覽器與技能 Worker 可個別重啟，不中斷核心身份。

## 下一階段提案 C：模型權重學習

權重更新不應直接消化所有網頁內容。先累積由任務、外部結果、人工偏好與驗證器產生的高品質資料，再離線訓練 LoRA／Adapter 候選。每個候選必須與固定基線比較，至少檢查能力提升、災難性遺忘、安全回歸、幻覺率與硬體成本；未通過就丟棄，不可替換線上模型。

## 技能知識圖

技能圖由現有 SQLite 記憶即時衍生，不建立第二份容易不一致的永久資料。它包含：

- `ECK 記憶 → 領域 → 子領域 → 技能／研究結果 → 來源`。
- 金色節點只表示已通過驗證且可重用的技能。
- 研究結論、反駁與證據不足結果不會偽裝成可執行技能。
- 每個來源保留 URL 或內部證據識別碼、類型、擷取時間與快照識別碼。
- 可攜認知包包含原始資料庫與技能程式；相容版本的 ECK 可重新建立相同技能圖。

## YouTube 與社群資料邊界

ECK 目前可以讀取允許自動化的公開文章、論文、程式庫與社群頁面並保留來源，但尚無「已驗證的 YouTube 影音內容學習」能力。YouTube 服務條款限制未經允許的自動化存取，而官方字幕下載 API 要求使用者具有影片編輯權限。因此 ECK 不會以非官方抓取方式假裝取得公開影片字幕。

合規路徑依序為：使用者提供逐字稿或授權媒體檔、內容擁有者 OAuth 授權字幕、作者另行公開且可合法下載的逐字稿。影音本身還需本機 ASR、畫面取樣、時間碼引用與多來源交叉查證後，才能進入研究記憶。
